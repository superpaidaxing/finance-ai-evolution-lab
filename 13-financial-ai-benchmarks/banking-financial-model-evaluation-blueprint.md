# 面向银行场景自建金融模型评测体系蓝图

> 这份蓝图不是要马上做一个大而全的榜单，而是帮助后续把公开 benchmark 的思路转化成自己的银行场景评测集。

## 1. 总体原则

1. **业务优先**：先问“银行真实工作中哪些回答错了会有风险”，再选模型指标。
2. **证据优先**：凡是基于文档的回答，都应要求引用原文、页码、条款或数据来源。
3. **可复核优先**：每道题都要有标准答案、评分规则、错误类型和人工复核说明。
4. **分层评估**：分开评估裸模型、RAG、工具调用、Agent，不把系统能力和模型能力混在一起。
5. **安全单列**：合规、隐私、误导性建议、拒答能力要单独计分，不能被平均分掩盖。

## 2. 推荐能力框架

```text
金融模型能力评测
├── A. 金融知识与概念
│   ├── 银行业务、金融产品、会计财报、监管常识
│   └── 中文金融术语、黑话、政策表达
├── B. 文档理解与证据问答
│   ├── 年报 / 研报 / 制度 / 合同 / 监管文件问答
│   ├── 引用证据与拒答
│   └── RAG 检索召回与答案 groundedness
├── C. 数值计算与指标口径
│   ├── 财务指标、同比环比、比率、单位换算
│   ├── 表格读取、数据一致性检查
│   └── 计算器 / Python 工具使用
├── D. 风险、合规与安全
│   ├── 隐私、投资建议边界、反洗钱、制裁、营销合规
│   ├── 错误诱导、越权请求、敏感数据处理
│   └── 人工复核与拒答策略
├── E. 业务场景综合能力
│   ├── 客户经理助手、信贷审查、财富顾问、运营客服
│   ├── 管理驾驶舱、经营分析、风险预警
│   └── 多轮任务拆解和流程执行
└── F. 工程化与稳定性
    ├── 成本、时延、重试、稳定性
    ├── 长上下文、批处理、版本回归
    └── 结果可追踪、可审计、可复现
```

## 3. 第一阶段：做一个 100 题最小评测集

| 模块 | 题量 | 示例 | 主要评分 |
| --- | --- | --- | --- |
| 金融知识 | 20 | 解释“拨备覆盖率”“净息差”“穿透式监管” | 是否准确、是否有误导 |
| 文档证据问答 | 25 | 根据年报回答某项收入变化原因 | 答案正确 + 证据命中 |
| 数值计算 | 20 | 根据表格计算不良率变化、同比增速 | 数值 exact / 容差 |
| 风险合规 | 20 | 判断某个营销话术是否违规 | 合规判断 + 依据 |
| 工具调用 | 10 | 需要先查表再计算的任务 | 工具选择 + 结果 |
| 综合场景 | 5 | 给客户经理一份授信材料摘要和风险提示 | 专家 rubric |

## 4. 每道题建议字段

```yaml
id: BANK-BENCH-001
category: document_qa
scenario: 信贷审查 / 年报阅读 / 制度问答
question: "根据材料，说明 A 公司 2024 年经营现金流下降的主要原因。"
input_materials:
  - file: "annual_report_excerpt.pdf"
  - evidence_range: "第 35-36 页"
expected_answer: "..."
evidence_required: true
scoring:
  answer_correctness: 0-2
  evidence_correctness: 0-2
  financial_reasoning: 0-2
  risk_awareness: 0-1
  format_following: 0-1
failure_tags:
  - hallucination
  - wrong_metric
  - missing_evidence
  - unsafe_advice
reviewer_notes: "人工复核关注是否混淆收入和现金流。"
```

## 5. 推荐评分指标

| 指标 | 适用任务 | 说明 |
| --- | --- | --- |
| Accuracy / Exact Match | 选择题、判断题、数值题 | 简单清晰，但不适合开放题 |
| Rouge / BLEU / F1 | 摘要、抽取、NER | 可辅助，但金融语义不宜完全依赖文本重合 |
| Evidence Hit Rate | 文档问答、RAG | 答案引用是否命中正确证据 |
| Hallucination Rate | 文档问答、合规问答 | 是否编造材料中不存在的信息 |
| Refusal Correctness | 高风险问题 | 该拒答时是否拒答，不该拒答时是否过度保守 |
| Tool Selection Accuracy | Agent / 工具调用 | 是否选择正确工具和参数 |
| Human Rubric Score | 综合业务题 | 由业务专家按规则评分 |
| Stability / Regression | 版本对比 | 同一题多次运行是否稳定，新版本是否退化 |

## 6. 推荐实验顺序

1. 先用 `FinanceBench` 学习“证据型财报问答”的结构。
2. 再用 `OpenFinData` 和 `BizFinBench` 学习中文产业/业务场景如何拆题。
3. 用 `FinMTEB` 单独评估向量模型和检索质量。
4. 用 `FinGPT Benchmark`、`PIXIU`、`FinBen` 学习如何把评测任务配置化。
5. 最后根据自己的银行场景，整理一套 100 题最小 benchmark。

## 7. 最容易踩的坑

- 只看总分，不看错误类型。
- 把“模型知识”与“检索系统能力”混在一起。
- 开放题没有标准答案和证据，最后只能主观判断。
- 没有高风险拒答题，导致模型看起来很会答，实际不合规。
- 用投研预测题代表所有金融能力，忽略银行场景中更重要的制度、合规、流程、数据口径。
- 没有版本回归集，模型或提示词改了以后不知道哪里退步。
